# GitHub

GitHub 同时指由 **GitHub, Inc.** 运营的商业平台和围绕该平台形成的产品品牌。公司官方资料写其成立于 2008 年 2 月、总部城市为旧金山；[[微软\|Microsoft]] 于 2018 年完成收购。技术背景只需一句：平台以 [[Git\|Git]] 仓库托管与协作为核心，把个人和组织身份、代码变更讨论、项目协作、自动化、制品、应用分发与企业管理放在同一服务关系中。

GitHub 不是 Git 项目的公司化名称，也不因托管 Git 的公开镜像而拥有 Git 的上游治理权。两者的公司、项目、代码版权、用户内容和商标层级见 [[Git 与 GitHub 的制度边界\|Git 与 GitHub 的制度边界]]。

## 实体身份与组织层级

- **合同与运营主体**：现行服务条款以 GitHub, Inc. 及其相关主体定义 “GitHub／we／us”；隐私声明又按场景区分 GitHub, Inc. 与 GitHub B.V. 的数据控制者角色。法律主体、平台品牌和具体产品不能互作无条件 alias。
- **母公司关系**：2018 年交易使 Microsoft 取得 GitHub 公司控制。GitHub 现行条款把 Microsoft 列为 affiliate，官方领导页也称其为 parent company。
- **管理层而非法定董事名册**：2026 年公开领导页列出 COO、CTO、CFO、CRO、CPO、CISO 等高管，并出现 “Office of the CEO”；本轮没有在该页找到可核验的现任 CEO 姓名，也没有取得 GitHub, Inc. 的现行完整法定董事名册。因此不从职称页面反推董事、逐级授权或具体报告线。
- **财务口径**：Microsoft 把 GitHub cloud services 纳入更大的 Intelligent Cloud／Azure and other cloud services 口径，但没有单列 GitHub 营收、利润、ARR、产品收入占比或客户合同额。

## 所有权与治理时间线

| 时间 | 事件 | 证据边界 |
|---|---|---|
| 2008-02 | GitHub 官方公司资料标示成立 | 不由此推断精确成立日、创始人清单或实时州登记 |
| 2018-10-19 | 欧盟委员会对 M.8994 Microsoft/GitHub 集中作出不反对决定 | 当时的合并审查结论不能证明 2026 年不存在新的竞争问题 |
| 2018-10-25 | Microsoft FY2019 10-K 记录完成收购 GitHub, Inc.，约 75 亿美元股票交易，并自该日起并表 | 会计收购日与公开公告日是不同口径 |
| 2018-10-26 | Microsoft 公开宣布完成交易，并称 GitHub 将独立运营、保持开放平台 | 这是收购时的管理承诺，不是否定公司控制的法律事实 |
| 2025-01 | Microsoft 建立 CoreAI 组织，把 GitHub 与其他平台和开发工具纳入同一战略组合 | 战略归组不证明 Microsoft 逐项决定 GitHub 的所有政策 |
| 2025-08 | GitHub 前 CEO 官方告别文称 GitHub 及领导团队作为 Microsoft CoreAI 的一部分继续；Axios 对内部备忘的报道交叉确认领导层向多名 Microsoft 高管汇报 | 支持组织整合加深，不支持“GitHub 已失去一切独立判断” |
| 2026-04 至本轮访问日 | 现行服务条款于 2026-04 生效；本轮访问的领导页和 Microsoft 财务材料继续显示母子公司、合同与业务整合 | 公开资料仍不足以还原完整股权链和法定董事会 |

因此，2018 年“独立运营”与 2025 年进入 CoreAI 不是同一时点的同义陈述。可以说最初承诺的独立运营边界后来被组织整合显著限定；不能在没有具体决策链时，把某次内容处置、产品改动或客户合同直接归因于 Microsoft 董事会。

## 产品线与客户

GitHub 的产品组合可按实体和付费关系分层：

- **基础平台**：Free 是个人、开源项目和团队的免费进入层；Team 与 [[GitHub Enterprise\|GitHub Enterprise]] 按用户收费。2026-08-11 的官方价格页标示 Team 为 4 美元／用户／月、Enterprise 从 21 美元／用户／月起，并同时出现“首 12 个月”的限定文字；地区、合同、促销和后续调价都可能改变实际成交价。
- **企业产品**：GitHub Enterprise 包含 GitHub 托管的 Enterprise Cloud 与客户管理基础设施的 Enterprise Server，并采用公开标价、试用和 contact sales 并行的采购路径。
- **AI 产品**：[[GitHub Copilot\|GitHub Copilot]] 采用个人、组织与企业席位，并逐步加入额度／用量计费。公开订户和组织数是采用指标，不能乘以标价当作收入。
- **第三方交易与分发**：[[GitHub Marketplace\|GitHub Marketplace]] 同时承载 GitHub 自有和第三方产品。现行开发者协议把 GitHub 定义为经平台购买产品的 merchant of record；第三方提供者以美元设价，GitHub 汇出售价的 95%并保留5%。客户向 GitHub 付款，但产品使用权、支持与主要产品责任仍来自提供者；该规则不披露 Marketplace GMV 或平台独立收入。
- **开源资金连接**：[[GitHub Sponsors\|GitHub Sponsors]] 把资助者与维护者连接起来，是开发者生态产品；本轮没有证据把它写成 GitHub 的主要收入线。
- **附加订阅与用量**：账单资料把收入路径区分为固定计划／席位、附加订阅和超出包含额度的用量；付款可经银行卡、PayPal、采购订单或连接的 Azure subscription。支付通道和 Microsoft volume licensing 的可用性不等于所有产品强制捆绑；企业合同主体、顺位和产品附加条款另见 [[GitHub Customer Agreement\|GitHub Customer Agreement]]。

官方价格页和客户材料展示 American Airlines、SAP、Spotify、Stripe、Ford、Nubank、Siemens 等企业案例。它们是经过选择的客户故事，不是完整或具有代表性的客户名录，也不披露合同金额、续约或效果。Microsoft FY2026 Q2 在 GitHub Copilot 语境下披露超过 470 万付费订户；Q3 称近 14 万组织使用 Copilot、enterprise subscribers 同比接近三倍。两组都是管理层时点口径，不是 GitHub 总客户数或单体财务报表。

## 商业模式与收入披露边界

可核验的商业模式是多层收费，而不是单一订阅：

1. 免费层形成个人、开源项目与组织的进入和协作基础；
2. Team／Enterprise 按席位收费，并由企业销售、支持和合同扩展；
3. Copilot 等产品采用席位加额度／用量；
4. 自动化、计算、存储和部分附加产品按订阅或超额用量收费；
5. Marketplace 对符合条件的第三方交易收取平台费用。

GitHub CRO 的官方简介把销售、客户成功、支持和运营纳入职责，并明确提到与 parent company Microsoft 扩大联合市场动作；账单和合同又允许 Azure subscription 与部分 Microsoft volume licensing 路径。它们支持销售、合同和组织协同，不能推出具体交叉销售收入、捆绑比例、销售佣金或客户被强制购买。

Microsoft FY2025 年报只在更大分部中列 GitHub cloud services。任何没有 Microsoft SEC 文件或 GitHub 一手拆分支持的 GitHub 单体营收、利润、ARR、Marketplace GMV、Copilot 收入或各业务占比，都应视为未核验数字。

## 开发者与组织生态

GitHub 在 2025 Octoverse 中自报超过 1.8 亿开发者和 6.3 亿仓库；这些数字显示平台聚集规模，却不等于活跃用户、付费客户或独立审计后的市场份额。公共仓库、组织身份、协作记录、应用市场和企业工作流共同构成平台生态，也使迁移不只涉及复制 Git 仓库，还涉及关系、权限、讨论和第三方服务。

同行评审研究把这种组织方式概括为 “connective coding”：平台配置并赋值公开仓库、开发者身份和组织资料。另一项对活跃 GitHub 仓库贡献网络的研究发现，公司雇员、志愿者和企业间选择性合作同时存在。两类研究帮助理解 GitHub 作为企业与开源交汇场所，但都不提供 GitHub 收入、全市场份额，也不能把所有开源贡献概括成无偿劳动或平台所有物。

Star 等平台可见指标还可能被购买和营销操纵；这会影响项目选择、招聘或融资判断，但不能仅凭异常指标判定具体项目有问题。详见 [[GitHub Star 信号污染\|GitHub Star 信号污染]]。

## 伙伴与竞争实体

- **母公司和销售伙伴**：[[微软\|微软]] 同时是所有权、组织整合、付款和联合市场动作的重要端点；这些关系仍须与每个具体合同和产品责任分开。
- **第三方产品提供者**：Marketplace 发布者与 GitHub 的交易中介角色分立；除 GitHub 自有产品外，第三方产品的许可、支持与责任通常由 Product Provider 承担。
- **主要商业竞争实体**：GitLab 的 FY2025 年报把 Microsoft 和 Atlassian 列为成熟竞争者；GitHub 与 [[GitLab\|GitLab]]、Atlassian 的 [[Bitbucket\|Bitbucket]] 在代码托管、协作、企业采购和相邻产品组合上竞争。
- **替代路径**：GitLab Self-Managed、Forgejo／Codeberg 等自托管或非营利平台说明用户存在退出路径；但本轮没有同口径的迁移成本或市场份额数据。

GitHub 的规模和生态密度可以解释其平台吸引力与一定的迁移成本，却不足以认定法定垄断、支配地位或精确市场份额。欧盟 2018 年批准收购只说明当时的交易审查结果，不是 2026 年市场力量的永久结论。

## 用户内容权利

2026-04-27 生效的服务条款把内容权利分为至少四层：

- 用户原则上保留其内容所有权，但须自行拥有发布与许可第三方内容的权利。
- 用户授予 GitHub 及其 affiliates 为提供、维护、开发和改进服务所需的许可；现行条款明确覆盖部分 AI 功能和模型训练。服务许可不是内容所有权转让。
- 公共仓库设置允许其他 GitHub 用户在平台功能范围内查看和 fork；仓库许可证通常授予超出平台 fork 功能的额外许可，但 ToS 不限制第三方依法获得的访问与使用权，其他合同和不可放弃的法定权利也可能相关。公开可见不自动等于具有任意开源许可证。
- 私有仓库按保密内容处理，但平台可在安全扫描、支持、服务完整性和法律义务等限定情形访问。不能写成平台绝不访问。

组织管理员的账户控制、上传者的内容权利、仓库许可证、贡献协议和 GitHub 的平台许可互不替代。账户或仓库被平台管理，也不自动解决代码来源、版权或专利链。

## 内容治理、法律请求与申诉

GitHub 作为私营平台保留删除或限制内容、暂停账户和终止服务的合同权力，同时建立了若干程序层：

- AUP 和 Community Guidelines 处理平台规则；
- 内部申诉通常可在决定后六个月内提出，官方称申诉由人作出，必要时由另一员工复核；
- DMCA 通知与 counter notice 处理版权主张，不是 GitHub 对权属的最终实体裁判；
- 政府内容下架须来自相关机构并标明具体内容与法律依据；GitHub 承诺通知、允许申诉、尽量地域限缩并公开请求；
- 用户资料请求依不同法律程序处理，不能与内容下架统计合并。

GitHub 2025 年自报收到 98 件政府下架请求、处理 3 件，涉及 1 个政府；另处理 650 件用户资料请求，其中 516 件发生披露，影响 2,249 个账户。这些是公司口径，不能证明每项请求合法、每次处置正确或统计已被独立审计。EFF 在 2019 年曾给予 GitHub 六项内容治理标准中的五项，缺项为申诉统计透明度；这是历史外部评估，不能平移为 2026 当前评级。

## 服务责任与证据边界

- ToS 的 as-is、as-available、无保证和责任限制条款分配合同风险，但不等于 GitHub 在任何法域和任何事实下绝对免责。
- Microsoft 收购 GitHub 公司，不等于收购 [[Git\|Git]] 项目、全部 Git 代码版权或上游治理。
- GitHub 托管、镜像或提供 fork 功能，不等于平台取得仓库内容所有权或保证其许可证和来源。
- 用户数、组织数、仓库数、订户数和公开标价回答不同问题，不能混算成收入、活跃度或市场份额。
- 收购时的独立运营承诺、后续 CoreAI 整合和具体产品／内容决定必须按时点分开。
- 学术论文与平台自报只能支持其各自样本和口径，不替代公司登记、监管决定、合同或财务披露。
